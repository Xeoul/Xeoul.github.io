Backing up my iPhone to my NAS over Wi-Fi

A containerized service on my home NAS backs up my iPhone every night over Wi-Fi, with no cable and no laptop. Getting there meant tracing three separate network and permission problems.

What it replaced

Backing up an iPhone normally means plugging it into a computer over USB and remembering to do it. I wanted it to happen on its own, to the NAS, and to land on a second disk for free: the NAS already copies itself to an external drive every night, so each phone backup is stored twice.

How it works

  • A Debian container (Docker Compose, on a UGREEN NAS) runs netmuxd. It finds the iPhone on the local network through mDNS (Bonjour) and connects with an existing trusted pairing record, so to the backup tools it looks like a USB connection.
  • A Bash scheduler runs idevicebackup2 at a set time, daily or weekly. Backups are incremental, so each run only transfers what changed.
  • Retries and a lock. If the phone isn't on the network, it tries again every 5 minutes for up to 2 hours. A lock file stops two backups from running at once.
  • Self-healing. A watchdog restarts netmuxd if it crashes, and Docker's restart policy brings the whole service back after a NAS reboot.
  • A log line per run (found, started, OK or failed), so a health check is a quick look at one file.

Three problems, and how I found each

1. The phone was unreachable from my laptop. ip route get showed why: my Tailscale subnet routes were sending local traffic into the VPN tunnel instead of over Wi-Fi. Rather than fight the routes, I moved the service to the NAS, which is wired and sits outside that problem.

2. The NAS couldn't discover the phone. avahi-browse traced it to Wi-Fi 7 MLO (multi-link operation): the multicast announcements on the MLO network weren't reaching wired devices. Moving the phone to the standard network fixed discovery. Direct port tests showed unicast still worked on MLO, so a connect-by-IP version is a possible later fix.

3. The container crash-looped with exit code 126. The image copied its scripts in readable only by root, while the container runs as a non-root user so the backup files stay owned by me. Setting explicit 755 permissions fixed it.

Keeping it locked down

  • No ports are exposed to the internet.
  • The pairing record is stored with restricted permissions (600 on files, 700 on folders).
  • The container runs as a non-root user.

Result

Hands-off iPhone backups to the NAS every night, with a second copy on an external drive. The manual step is gone, and the setup recovers from crashes and reboots by itself. It's the same home-lab approach as the AI agent on my NAS: a small container with the least access it needs.
